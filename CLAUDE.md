## The four roles → actual role strings

- **admin** — approves/rejects shop registrations, manages subscription tier definitions, platform-wide monitoring.
- **shop_owner** — full control of their shop(s): profile, catalog, pricing, branches, staff, appointments, analytics.
- **branch_manager** — owner-adjacent permissions scoped to a branch (see route middleware below).
- **staff** — day-to-day execution: jobs, appointments, customers, measurements; cannot delete/reassign or see owner-only financials.
- **customer** — just a `User` with the `customer` role; there is no separate `CustomerProfile` model (the approved thesis ERD describes one, but the real schema doesn't have it — trust the code, not the paper diagram).

Role enforcement is via `role:` middleware in `routes/api.php`, e.g. `Route::middleware('role:shop_owner,branch_manager,staff')`. When adding an endpoint, match the narrowest role set that actually needs it — see the comments already in `routes/api.php` explaining *why* certain actions (discounts, staff reassignment, deletes) are owner/manager-only while day-to-day CRUD (measurements, job status updates, walk-in catalog orders) is open to staff too.

**Catalog + Service management is branch_manager-writable too (2026-09-28)** — `CatalogController::store/update/destroy` and `ServiceController::store/update/updateSale/restore/destroy` (plus `ServicePackageController`'s write actions) moved from `role:store_owner` to `role:store_owner,branch_manager` in `routes/api.php`. This was a real bug, not a deliberate restriction: the dashboard sidebar has always shown "Catalog Designs" and "Services" to `isStoreOwner || isBranchManager` (`dashboard/layout.tsx`), but the backend 403'd every branch manager write until this fix — confirmed via real HTTP requests (`php artisan serve` + `curl`, not `$kernel->handle()` called repeatedly in one process, which silently reuses the first request's resolved auth user and gives false negatives on subsequent calls in the same script). **`StoreServiceRequest::authorize()` is a second, independent gate** on top of route middleware — updating the route alone wasn't enough for Services; the FormRequest's own hardcoded `hasRole('store_owner')` check needed the same `|| hasRole('branch_manager')` update, the same "coarse role check, real scoping lives in the controller" pattern `StoreStaffRequest`/`UpdateStaffRequest` already use. Catalog items and Services have no `store_branch_id` column — this grant is store-wide, not scoped to the manager's own branch the way Staff/Jobs/Appointments already are. Audit Log, cross-branch analytics (`/analytics/branches`, `/analytics/staff`), subscription activity, Special Hours, Store Posts, and Support Tickets stay `store_owner`-only — none of those are shown to branch managers in the nav.

`role:` middleware alone can't express "only your own branch," so per-branch scoping is enforced inside the controller: `JobOrderController::branchAccessDenied()`/its list-scoping in `index()`, and (as of 2026-09-27) the same pattern in `StaffController::index()`/`show()` — a `branch_manager`/`staff` account pinned to a branch (`staffProfile->store_branch_id`) only ever sees that branch's own roster, not the whole store's. `StaffController::store()`/`update()`/`destroy()` (staff CRUD) are also open to `branch_manager` now, not owner-only — routed through `StaffController::staffManagerCrudDenied()`, which lets a branch manager hire/edit/deactivate staff within their own branch only, and never lets them promote anyone to branch manager or touch another branch manager's account (both stay owner-only). `JobOrderController::notifyOwnerOfActivity()` also now notifies the relevant branch's manager (not just the store owner) when the activity happened on their branch.

**Branch Management has the exact same per-branch-scoping shape (2026-09-28)** — `StoreBranchController::branchManagerCrudDenied()` (mirrors `staffManagerCrudDenied()`'s docblock reasoning) lets a branch manager `update()` **only their own branch** (`staffProfile->store_branch_id === $branch->id`), and never lets them touch `manager_id` on the update payload (reassigning who manages a branch is a promotion/demotion action, same "never lets them promote to branch manager" rule as Staff). `store()` (add a new physical branch), `setMain()`, and `destroy()` stay `store_owner`-only in `routes/api.php` — bigger structural decisions than editing an existing branch's hours/contact/location, unlike the update route which moved to `role:store_owner,branch_manager`. `resolveMapsLink()` (the Google Maps paste-link helper) moved there too since it's just a stateless coordinate lookup used by both the add and edit forms. **Gotcha hit while building this**: writing the moved routes as `/stores/{store}/branches/{branch}` inside a group that's *already* prefixed with `stores/{store}` produces a duplicate `{store}` route parameter and throws `LogicException` at boot — the fix is the same relative-path style every other route in that group already uses (`/branches/{branch}`, not the full path). The frontend (`dashboard/branches/page.tsx`) mirrors this: `isStoreOwner` gates the Add/Delete/Set-Main actions entirely, and a wrapped `handleEditClickGated()` blocks (with a toast, not a silent no-op) a branch manager editing any branch that isn't `staffProfile.store_branch_id`.

## Job order tracking — the actual state machine

From `app/Models/JobOrder.php` and its migrations — this is ground truth, not the thesis paper's idealized 13–19-stage tables. **This replaced an earlier, simpler `pending → cutting → sewing → fitting → ready_for_pickup → completed` version — if you see that old sequence cited anywhere (old docs, old memory, stale comments), it's out of date.**

- `JobOrder::STATUSES` — the real, current "3-Phase Tailoring Tracker" pipeline: `pending → design → pattern_making (or mass_cutting_printing, the Bulk Order Override for jobs with a Team Roster/Size Sheet) → cutting → sewing → ready_for_fitting → final_adjustments → qc_ironing → ready_for_pickup → completed`, with `cancelled`, `rejected`, and `on_hold` reachable from most points. `ready_for_fitting` auto-creates a Fitting appointment for the customer; `final_adjustments` is the revert target when a fitting reveals issues (job either goes back to `sewing` for rework or forward to `qc_ironing`).
- `payment_status`: `unpaid → partial → paid`.
- `JobOrder::STAFF_STAGES`: `design, pattern_making, cutting, sewing, qc_ironing` — the internal production stages staff progress through, distinct from the customer-facing `status`. **No more manual pre-assignment** (2026-09-27 — the old `assignStaff()` endpoint/route and `StaffAssignedNotification` are gone): `JobOrderController::update()` auto-upserts a `job_order_staff` row (`JobOrderStaff`) whenever anyone moves a job's status into/out of a `STAFF_STAGES` value — whoever actually made the transition is recorded as having worked that stage, and `assigned_staff_id` becomes "last person who touched this job," not "who the owner assigned." `mass_cutting_printing` maps onto the `pattern_making` stage key for this purpose (bulk's override of that phase). **One row per stage** still holds, so a staff member with multiple open stages on the same job has multiple pivot rows — any "how many jobs is this person on" count must `COUNT(DISTINCT job_order_id)`, not a raw row count (this exact bug shipped once and was fixed in `StaffController::index`/`show` — the fix and the productivity-counting logic are unaffected by the auto-attribution change, same table/shape, just populated automatically now).
- `JobOrder::STAGES_REQUIRING_DOWNPAYMENT` and `MATERIAL_SOURCES` (`shop_supplied`, `customer_supplied`) also live as constants on this model — check them before adding new business rules around payment gating or material handling. The 50% downpayment gate ("No DP, No Layout, No Cut") is enforced in `JobOrderController::update` via `JobOrder::requiresDownpaymentFor()` — repairs are exempt unless the shop turns on `stores.repair_requires_downpayment` (default off, many shops charge repairs at pickup). "Paid so far" there is `total - balance - discount_amount`, measured against 50% of `total - discount_amount`.
- `is_rush` is a boolean flag added after the initial schema (rush fee logic). The old `is_outsourced`/`partner_store_name`/`outsourcing_cost` fields were **removed** (2026-09-27) — subcontracting maps to no objective and edges into logistics/expense tracking.
- `tracking_code` (unique 8-char string, server-generated in `JobOrderController::store`) lets a customer check order status without logging in, via the public `GET /track/{trackingCode}` route (`JobOrderTrackingController`, narrow safe field subset, no staff/internal data). **Backend/DB only — deliberately no frontend page for this yet**, don't build one unless asked.
- `ready_for_pickup_at` (server-derived timestamp, stamped on transition into that status) drives the Reports page's "Unclaimed Pickups" list — orders sitting ready 14+ days, with a matching daily proactive notification (`app:notify-unclaimed-pickups`).
- Completion photo upload (`completion_photo_url`) is available at QC time but **optional, not required** — a hard "no photo, no ready-for-pickup" gate was tried and explicitly reverted by the shop owner.
- `discount_amount` is a real column that `JobOrderController::applyDiscount` writes to, reducing `balance` directly (never `total_amount`) — **any revenue/paid calculation must be `total_amount - balance - discount_amount`, never just `total_amount - balance`**, or a discount silently gets counted as cash collected. This exact bug shipped across ~11 surfaces (frontend and backend) before being fixed everywhere; if you add a new revenue figure anywhere, use this formula from the start.
- **Payment verification (2026-09-27)**: a `Payment` is no longer "logged = counted." Cash auto-verifies immediately at `JobOrderController::pay()` (the money's physically in hand) and applies to `balance`/`payment_status` right away, same as before. GCash/PayMaya do not — they sit as `pending_verification` (derived from `verified_at`/`rejected_at` via `Payment::getStatusAttribute()`) until an owner/branch manager calls the new `verifyPayment()` endpoint, which is the only thing that actually reduces the balance for those methods. `receipt_path` is now `required_if` for gcash/paymaya (it's the artifact being verified against), and cash requires `cash_tendered` (`change_amount` is server-computed, `tendered - amount`). `rejectPayment()` only reverses the balance if the payment was already verified — a still-pending one was never applied, so rejecting it is a no-op on balance. The customer-facing tracker (`JobOrderTrackingController`) exposes a `pending_payment_amount` field (sum of a job's still-pending payments) precisely so a customer who just paid via GCash isn't left staring at an unchanged balance with no explanation.

## Appointment scheduling rules (customer travel buffer + early arrival, 2026-09-28)

From `app/Models/Appointment.php` — ground truth for both the public booking flow and the owner/staff dashboard:

- **Cross-shop travel buffer**: `Appointment::hasCustomerScheduleConflict()` blocks a new booking not just on a literal time overlap, but whenever it falls within `Appointment::CUSTOMER_TRAVEL_BUFFER_MINUTES` (30 min) of another **active** (`pending`/`confirmed`/`in_progress`) appointment the same customer holds **at any store**, not just the one being booked. Branch, shop, and service never factor into this check — a customer booking two *different* services at two *different* shops is blocked by a too-tight gap exactly the same as booking the same service twice. The check is duration-aware: it's `previous.scheduled_at + previous.duration_minutes + buffer <= next.scheduled_at`, not a bare overlap of start times — two back-to-back appointments with zero travel time between them are blocked even though their time windows don't technically overlap. `cancelled`/`rejected`/`no_show`/`completed` appointments never count, so cancelling one immediately frees the customer's schedule for a conflicting booking elsewhere. Only wired into `PublicBookingController::submit()` today (the customer-facing flow) — not the owner-side manual booking/reschedule paths, which use the unrelated `hasSchedulingConflict()` (branch-capacity check, not customer-schedule check).
- **Early-Arrival Accommodation**: `checked_in_at` (existing Staff Check-In action, written via a plain `PUT .../appointments/{id}` with `{checked_in_at}`) now also auto-derives `arrival_status` (`on_time`/`early`/`late`, ±5min grace window around `scheduled_at`) server-side in `AppointmentController::update()` — **never trust an `arrival_status` from the client**, it isn't even accepted as input. `scheduled_at` itself is never rewritten when a customer arrives early or late; the actual event lives in separate columns (`arrival_status`, `early_arrival_decision`, `actual_service_start_at`, `accommodated_by_id`) so "Scheduled Time ≠ Actual Arrival" holds in the data, not just the UI copy. When an appointment is flagged `early`, staff/owner can PUT `{early_arrival_decision: 'accommodated'}` to start service now — gated by a capacity check (`hasSchedulingConflict()` against the time between now and the original scheduled start) so an early customer can **never** automatically displace another confirmed appointment on the same branch — or `{early_arrival_decision: 'waiting'}` to leave the customer queued for their original slot. Every accommodation is audit-logged (`appointment_early_arrival_accommodated`).

**`GET /catalog` read-scope fix (2026-09-28)** — same shape as the `service-packages` fix below: `CatalogController::index` was left `role:store_owner`-only even though Catalog's own write actions (`store`/`update`/`destroy`) already moved to `role:store_owner,branch_manager`, and the Catalog Designs nav is shown to `isStoreOwner||isBranchManager`. A branch manager could create/edit/delete catalog items but couldn't load the list to see what already exists. Moved the read route to sit with its own write actions.

**`GET /service-packages` read-scope fix (2026-09-28)** — this stayed `role:store_owner`-only even after Service Packages' own write actions (`store`/`update`/`destroy`) moved to `role:store_owner,branch_manager`, and even though the Services nav (with its Packages tab) is shown to plain staff too. A branch manager who could create/edit/delete packages couldn't even list them, and staff got a flat 403 just opening the Packages tab despite having read access to every other Services resource. Moved to sit alongside `GET /services` in the shared `role:store_owner,branch_manager,staff` group.

## Known bug pattern: capped-list counts (recurred 7+ times, watch for it in new code)

The single most common bug class found this session: a frontend badge/count/alert derived by filtering a **capped or paginated fetch** (`per_page: 200`, `.take(20)`, etc.) instead of querying a **dedicated, unbounded `->count()`**. Once real data volume exceeds the cap, older-but-still-relevant records silently vanish from the derived count — nothing errors, the number is just quietly wrong. Fixed across: notification unread badge, `AnalyticsController`'s Home-dashboard alerts (`completed_unpaid_jobs_count`, `pending_dp_jobs_list_count`, `due_today_jobs_count`, `due_this_week_jobs_count`), `JobOrderController::index`'s tab badges (`walk_in_count`/`online_count`/`pending_count`) and search (moved server-side once the 200-cap made client-side search unreliable), and Payments' Job Balances tab (`unpaid_only` query param replacing a client-side filter downstream of a `per_page: 500` fetch).

**The fix pattern**: build the query once, `clone` it before applying `->take()`/`->paginate()` for the *display* list, and run `->count()` on the unclosed clone for the *badge/total*. The count query and the display-list query must be independent — the count is never allowed to be bounded by what the list can show. Apply this same pattern to any new dashboard count/badge added in the future; don't derive a total from a capped array.

- `ShopController::show()` (the owner's authenticated shop endpoint) used to skip the `reviews_count`/`reviews_avg_rating` computation that the anonymous `publicProfile()` endpoint always did — a storefront-preview-vs-owner-dashboard data mismatch. Fixed to call `loadCount('reviews')`/`loadAvg('reviews', 'rating')` identically in both. If you add a new computed/aggregate field to one of these two endpoints, add it to both — they're meant to describe the exact same shop.

See `sutura-client/DEADLINE.md` for the full migration plan. **A low-stakes dry run of this migration was already done (2026-07-23) against a disposable Supabase + R2 project** — full detail in this project's Claude memory (`project_postgres_migration_test_bugs_fixed.md`, `project_r2_storage_connected_url_bug_fixed.md`), summary here:

- `league/flysystem-aws-s3-v3` — **installed**, not pending anymore.
- `FileUploadController`'s URL bug — **fixed**. It now uses a single `private const UPLOAD_DISK = 'public'` referenced by both the `store()` and `Storage::disk(...)->url()` calls in all 4 methods. **Don't call bare `Storage::url($path)` or hardcode `'public'`/`'s3'` in more than one place here again** — the original bug was exactly that drift (store used one disk, url-generation silently used a different default disk). When the real Sept switch happens, changing that one constant to `'s3'` is the entire migration for this file.
- MySQL/Postgres `LIKE` case-sensitivity — **already hit and fixed**, not just a theoretical risk. `CatalogController::index()`'s search used to silently return zero results on Postgres for any non-exact-case search term (verified: searching `"gown"` found 0 of 10 real matches). Fixed with `whereRaw('LOWER(name) LIKE ?', ['%'.strtolower($search).'%'])`. **This is the pattern to use for any future user-typed search/filter field** — plain `LIKE` is not portable between MySQL and Postgres, `LOWER()` on both sides is.
- **New bug class found during the dry run, now fixed**: `varchar(255)` columns storing image/file URLs (`shops.logo_path`, `catalog_images.image_url`, `catalog_items.fabric_image_url`/`size_chart_image_url`/`external_gallery_url`, `services.size_chart_image_url`, `payments.receipt_path`, `catalog_orders.payment_receipt_path`, `appointments.payment_receipt_path`) are too narrow for real cloud storage URLs (domain + bucket + URL-encoded filename routinely exceeds 255 chars) — Postgres rejects the write outright rather than silently truncating like MySQL might. Widened all of them to `TEXT` in `2026_07_23_225530_widen_image_and_path_url_columns_to_text.php`. **If you add a new URL/path column, make it `TEXT` from the start, not `string()`.**
- `LocalTestSeeder.php`'s shop `logo_path` was hardcoded to `http://127.0.0.1:8000/...` — only ever worked on one machine with the server on that exact port. Fixed to `Storage::disk('public')->url(...)`, same pattern as the controller fix above.
- **Seeded data doesn't automatically generate notifications.** `LocalTestSeeder.php` writes job orders/payments/appointments/staff assignments straight to Eloquent (`updateOrCreate`, pivot inserts), bypassing the controllers where notification-firing actually lives (`JobOrderController@store`, payment/appointment endpoints) — so a freshly reseeded shop with a full realistic dataset had **zero** rows in the `notifications` table, which looked like a bug but was a seeder coverage gap. Fixed by explicitly firing the real `Notification` classes (`PaymentReceivedNotification`, `AppointmentBookedNotification`, `NewJobOrderNotification`) against the already-seeded `$jo1`–`$jo11`/staff/appointments, then staggering `created_at` and marking roughly the older half `read_at` (never all-read or all-unread) so the bell/Notifications page shows a believable mix. Since `notify()` has no dedup (unlike `updateOrCreate` elsewhere in this file), the block clears `$owner`/relevant staff's prior notifications first — **don't remove that clear-before-reseed step**, or re-running `db:seed` doubles them up. (`StaffAssignedNotification` was removed 2026-09-27 along with manual staff pre-assignment — don't reintroduce a seeder call to it.)
- **Second Shop Owner test account**: `owner2@sutura.com` / `password`, shop "Bautista Custom Tailors" (`bautista-tailors`, Basic plan trial, one branch, no jobs/catalog — a login fixture for multi-tenant-isolation and lower-tier-plan testing, not a second fully-populated demo shop).
- `LocalTestSeeder.php` now creates 11 job orders (`$jo1`–`$jo11`, `updateOrCreate` keyed on `['shop_id', 'order_number']`) — `$jo9`/`$jo10`/`$jo11` (JO-1009/1010/1011) were added specifically so every Home-dashboard alert widget above has at least one real row to show after a fresh reseed (a completed-but-unpaid job, a job due today, and a genuinely-still-`unpaid` pending job respectively). **`$jo2` gets a `Payment::create()` later in the same seeder that converts it from seeded `unpaid` to `partial`** — if a future widget needs an `unpaid` job to test against, don't assume `$jo2` still qualifies; check the live DB value (`php artisan tinker`), the seeder's static source isn't the full story once side effects like this run. Note: `php artisan test` is off-limits this project cycle — it wiped the real local dev DB once already; use `php artisan db:seed` (safe to re-run, no duplicates) to refresh test data instead.
- `config/cors.php` still doesn't exist — still not needed until frontend/backend are on separate domains (Vercel + Railway). Still pending, unlike everything else in this list.
- **`Cache::remember()` must store plain arrays, never a `Collection`/object.** `SystemNewsController::index()` cached `->values()` (a `Collection`) directly; a `composer update` regenerating the autoloader mid-TTL broke the cached blob's `unserialize()`, coming back as `__PHP_Incomplete_Class` — which `json_encode`s as `{}` instead of `[]`, crashing the frontend's `.map()` with "items.map is not a function" even though the frontend code was correct. Fixed by caching `->all()` instead. If you add a new `Cache::remember()`, always store the plain-array/scalar result, not an Eloquent Collection/model instance — the failure mode is silent until something (a deploy, a composer update, a class rename) shifts autoloading during the cache's TTL.
- **Dependency security scan (2026-08-13)**: `composer audit` found 17 advisories (mostly `guzzlehttp/guzzle` 7.11.1, high/medium severity) — all transitive deps with permissive constraints, fixed with `composer update guzzlehttp/guzzle guzzlehttp/psr7 league/commonmark --with-all-dependencies` (no Laravel version change). `composer audit` now reports zero.
